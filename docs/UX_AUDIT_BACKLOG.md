# UX/UI audit backlog

Дата аудита: 2026-06-14

Роль аудита: UX/UI + Product Manager.

Цель: привести RentCRM от технического MVP к рабочему SaaS-кабинету, за который малый арендодатель готов платить.

## 1. Executive summary

Текущий интерфейс функционально покрывает основные сущности: объекты, арендаторы, договоры, платежи, заявки, документы, расходы, лиды, уведомления и подписку. Но пользовательский опыт пока воспринимается как техническая консоль:

1. На экране слишком много равнозначных карточек и действий.
2. Нет понятного пошагового сценария первого запуска.
3. Формы используют технические поля и значения.
4. Нет нормального выбора объекта/арендатора/договора при создании связанных сущностей.
5. Опасные действия доступны без подтверждения.
6. Мобильный вид работает, но занимает много вертикального места и плохо сканируется.
7. Настройки уведомлений и оплаты слишком технические для малого арендодателя.

Главный UX-вектор: меньше технического шума, больше контекстных сценариев: "добавить объект", "заселить арендатора", "создать договор", "контролировать оплату", "принять заявку".

## 1.1. Реализовано в первой UX-итерации

1. Добавлен onboarding "Быстрый старт" для нового аккаунта.
2. Быстрые действия стали контекстными по разделам: больше нет одинаковой сетки из 9 действий на каждом экране.
3. Формы получили нормальные контролы: select, checkbox, date, number.
4. Для платежей, договоров, заявок, документов, расходов, объявлений и лидов добавлен явный выбор объекта; где нужно, добавлен выбор арендатора.
5. Статусы в списках выводятся по-русски и получили цветовую иерархию.
6. Удаление платежей, объектов, арендаторов, заявок, документов, расходов, лидов и объявлений требует подтверждения.
7. E2E Playwright остается зеленым после UX-правок.
8. Добавлен drawer просмотра и редактирования для объектов, арендаторов, договоров, платежей, заявок, документов, расходов, объявлений и лидов.

## 2. P0: критично перед демонстрацией клиентам

### UX-001. Сделать onboarding вместо пустой сводки

Проблема: после регистрации пользователь видит 6 нулевых метрик, 9 быстрых карточек и пустые панели. Непонятно, с чего начать.

Решение:

1. Если объектов нет, показывать onboarding checklist:
   - Добавьте первый объект.
   - Добавьте арендатора.
   - Создайте договор.
   - Проверьте платежный календарь.
   - Настройте уведомления.
2. Primary CTA на первом шаге: "Добавить объект".
3. После выполнения шага отмечать его выполненным и переводить к следующему.

Критерий готовности:

1. Новый пользователь без данных видит один главный сценарий, а не все функции сразу.
2. После добавления объекта следующий рекомендуемый шаг меняется на арендатора.

### UX-002. Убрать универсальную сетку "быстрого создания" со всех разделов

Проблема: в каждом рабочем разделе отображаются все 9 сущностей. Это создает ощущение перегруженности и не помогает задаче раздела.

Решение:

1. В разделе "Объекты": кнопки "Добавить объект", "Добавить арендатора", "Создать договор".
2. В разделе "Платежи": "Добавить платеж", "Сформировать платежи по договору", фильтр периодов.
3. В разделе "Заявки": "Создать заявку".
4. В разделе "Документы": "Загрузить документ".
5. В разделе "Финансы": "Добавить расход".
6. В разделе "Лиды": "Добавить объявление", "Добавить лид".
7. В "Сводке" оставить только onboarding или 2-3 главные быстрые команды.

Критерий готовности:

1. На каждом разделе видны только контекстные действия.
2. Нет disabled-карточек без объяснения.

### UX-003. Заменить технические поля на нормальные контролы

Проблема: поля вроде `Уведомления true/false`, `SMS test=1`, `Telegram chat_id`, `Generic payment URL`, статусы `VACANT`, `PLANNED`, `DONE` выглядят как технический прототип.

Решение:

1. Boolean-поля заменить на checkbox/switch.
2. Статусы показывать по-русски:
   - `VACANT` -> "Свободен";
   - `OCCUPIED` -> "Занят";
   - `PLANNED` -> "Запланирован";
   - `OVERDUE` -> "Просрочен";
   - `PAID` -> "Оплачен";
   - `NEW` -> "Новая";
   - `IN_PROGRESS` -> "В работе";
   - `DONE` -> "Закрыта".
3. Типы объектов, документов, платежей сделать select.
4. Даты сделать date input.
5. Деньги сделать numeric input с рублевым суффиксом и форматированием.

Критерий готовности:

1. Пользователь не видит enum/boolean/string-значения из backend.
2. Все поля имеют человекочитаемые подписи и подсказки.

### UX-004. Сделать выбор связанной сущности, а не автоподстановку первой записи

Проблема: платежи, договоры, заявки, документы, расходы и лиды привязываются к первому объекту/арендатору из store. Для реального арендодателя с 5-50 объектами это опасно.

Решение:

1. В формах добавить select "Объект".
2. В формах договора/платежа/заявки добавить select "Арендатор".
3. В платежах добавить select "Договор", если есть активные договоры.
4. При пустом списке показывать подсказку: "Сначала добавьте объект".

Критерий готовности:

1. Пользователь явно выбирает объект и арендатора.
2. Нельзя случайно создать платеж не к тому объекту.

### UX-005. Подтверждение удаления и защита опасных действий

Проблема: кнопка "Удалить" доступна прямо в строке без подтверждения. Можно случайно удалить платеж, объект или документ.

Решение:

1. Для удаления показывать confirm modal.
2. В modal писать, что именно будет удалено.
3. Для объектов с договорами/платежами предупреждать о связанных данных.
4. Использовать secondary danger action, не делать "Удалить" визуально равным основным действиям.

Критерий готовности:

1. Удаление невозможно одним случайным кликом.
2. Пользователь понимает последствия.

## 3. P1: важно для платного UX

### UX-006. Разделить список и создание через drawer/modal

Проблема: формы раскрываются прямо внутри сетки карточек. При росте данных интерфейс станет тяжелым.

Решение:

1. Основная область раздела должна быть списком/таблицей.
2. Создание и редактирование открывать в drawer справа или modal.
3. Один главный CTA в шапке раздела.

Критерий готовности:

1. Раздел выглядит как рабочий список, а не как набор форм.
2. Создание не ломает компоновку страницы.

### UX-007. Добавить таблицы, фильтры и поиск

Проблема: строки сейчас похожи на простые карточки. При большом количестве объектов нужны поиск, сортировка и фильтры.

Решение:

1. Объекты: фильтр по статусу, поиск по адресу/названию.
2. Платежи: период, статус, объект, просроченные.
3. Заявки: статус, приоритет, объект.
4. Документы: тип, срок истечения.
5. Финансы: месяц, категория, объект.
6. Лиды: статус, источник, объект.

Критерий готовности:

1. Пользователь может найти нужную запись за 2-3 действия.
2. Списки остаются удобными при 50 объектах и сотнях платежей.

### UX-008. Улучшить empty states

Проблема: empty states сейчас информируют, но не ведут пользователя к действию.

Решение:

1. "Добавьте первый объект" + кнопка "Добавить объект".
2. "Платежей пока нет" + объяснение, что платежи появятся после договора.
3. "Документов нет" + кнопка "Загрузить договор".
4. "Лидов пока нет" + кнопка "Создать объявление".

Критерий готовности:

1. Каждый пустой блок содержит следующий полезный шаг.

### UX-009. Переработать мобильную навигацию

Проблема: на мобильном вся навигация идет горизонтальной длинной полосой, затем большая кнопка "Выйти", затем метрики вертикальной простыней. Первый полезный контент далеко.

Решение:

1. На mobile использовать компактный верхний bar с названием и menu button.
2. Основные разделы вынести в bottom navigation: Сводка, Объекты, Платежи, Заявки, Еще.
3. Остальные разделы спрятать в "Еще".
4. Метрики на mobile сделать 2 колонки или горизонтальный scroll с compact cards.
5. Кнопку "Выйти" убрать в меню профиля.

Критерий готовности:

1. На экране 390px пользователь видит заголовок раздела, главный CTA и часть списка без длинного проскролла.

### UX-010. Переработать настройки уведомлений

Проблема: форма уведомлений выглядит как техническая интеграционная панель. Telegram включен, но токена нет; SMS test=1 непонятен; chat_id непонятен большинству клиентов.

Решение:

1. Разделить на простые блоки:
   - Когда отправлять.
   - Текст сообщения.
   - Каналы.
   - История отправок.
2. Показывать настройки канала только если канал включен.
3. Добавить кнопку "Проверить отправку" для каждого канала.
4. Для Telegram добавить подсказку "Как получить chat_id".
5. По умолчанию не включать канал без настроек.

Критерий готовности:

1. Пользователь понимает, что включено и почему уведомление может не уйти.
2. Ошибки провайдера видны рядом с каналом.

### UX-011. Разделить "Подписка" и "Прием оплат от арендаторов"

Проблема: в разделе подписки рядом находятся тарифы SaaS и настройки провайдера оплаты. Для клиента это смешивает две разные задачи:

1. Оплатить подписку RentCRM.
2. Настроить прием платежей от арендаторов.

Решение:

1. "Подписка": текущий тариф, лимит объектов, счет, история оплат, кнопка "Перейти на тариф".
2. "Прием оплат": ЮKassa/СБП/ссылка оплаты, реквизиты, комиссии, тестовый режим.
3. Не показывать секретные ключи рядом с выбором тарифа без объяснения.

Критерий готовности:

1. Клиент не путает оплату сервиса с оплатами арендаторов.

## 4. P2: улучшения качества и доверия

### UX-012. Улучшить экран входа и регистрации

Проблема: поля предзаполнены демо-данными. Для production это снижает доверие.

Решение:

1. Убрать предзаполненные email/password.
2. Добавить ссылку на пользовательское соглашение и политику ПДн.
3. Показать требования к паролю.
4. Добавить "Забыли пароль?".

Критерий готовности:

1. Экран выглядит как production SaaS, а не demo stand.

### UX-013. Добавить человекочитаемые ошибки

Проблема: сейчас ошибка может быть просто "Ошибка запроса".

Решение:

1. На frontend маппить частые ошибки:
   - email занят;
   - неверный пароль;
   - достигнут лимит объектов;
   - не заполнены обязательные поля;
   - провайдер уведомлений не настроен.
2. Ошибку показывать рядом с формой/полем.

Критерий готовности:

1. Пользователь понимает, что исправить.

### UX-014. Добавить detail/edit сценарии

Проблема: сейчас есть быстрые действия, но нет полноценного просмотра объекта, договора, платежа или заявки.

Решение:

1. Клик по строке открывает detail drawer.
2. Внутри detail:
   - основные данные;
   - история действий;
   - связанные платежи/документы/заявки;
   - редактирование.

Критерий готовности:

1. Пользователь может разобраться в конкретном объекте без перехода между 5 разделами.

### UX-015. Добавить визуальную иерархию статусов

Проблема: все статусы выглядят одинаковыми серыми бейджами.

Решение:

1. Оплачен: зеленый.
2. Просрочен: красный.
3. Запланирован: нейтральный.
4. В работе: синий/акцентный.
5. Закрыта: серый.

Критерий готовности:

1. Просрочка и проблемы считываются за секунду.

## 5. Рекомендуемый порядок разработки

1. UX-003: русификация статусов и нормальные контролы.
2. UX-004: явный выбор объекта/арендатора/договора.
3. UX-001: onboarding для пустого аккаунта.
4. UX-002 + UX-006: контекстные CTA и drawer/modal создания.
5. UX-005: подтверждение удаления.
6. UX-007: фильтры и поиск.
7. UX-010 + UX-011: настройки уведомлений и разделение подписки/приема оплат.
8. UX-009: мобильная навигация.

## 6. Definition of done для UX-итерации

1. Новый пользователь за 3 минуты создает объект, арендатора и договор без подсказок разработчика.
2. Пользователь явно понимает, к какому объекту относится платеж/заявка/документ.
3. На экране нет технических enum/boolean/string-значений.
4. Опасные действия требуют подтверждения.
5. На mobile первый полезный контент виден без длинной прокрутки.
6. Playwright e2e покрывает onboarding, создание сущностей через новые формы, фильтры, подтверждение удаления и mobile smoke.
