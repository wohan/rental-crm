# Проверка и развёртывание агента 0.2

Ветка `codex/text-agent-production`, основана на `codex/text-agent-integration`. Пакеты собраны из исходников в `backend/vendor/text-agent` и `frontend/vendor/text-agent-react-source`; React устанавливается из `text-agent-react-0.2.0.tgz`. Внешний Maven/npm registry не нужен.

## Изменения

Полный OpenAPI генерируется из реальных контроллеров и доступен авторизованному пользователю на `/api/openapi`. Snapshot `backend/src/main/resources/rental-openapi.json` включает 66 операций; 19 разрешены агенту. Контракт кэшируется при запуске. `/api/text-agent/operations` показывает каталог и причины отключения остальных операций.

Разрешены list/create для арендаторов, объектов, договоров, платежей, расходов, обслуживания, объявлений, лидов и документов, плюс markPaymentPaid. Создание документа означает сохранение ссылки; загрузка файла не поддерживается. PUT/DELETE, auth, billing и технические действия отключены. ID связанных сущностей нужно указать явно; можно сначала запросить список.

Flyway V10 добавляет agent_sessions, agent_audit, agent_rate_limits и agent_admission. Состояние хранится зашифрованным в PostgreSQL; CAS защищает одно подтверждение от повторной отправки между репликами и после перезапуска. Audit содержит метаданные без текстов/токенов. Виджет восстанавливает сессию после обновления страницы и показывает разрешённые поля результата.

## Подготовка сервера

Сохраните существующий `.env`, сделайте резервную копию PostgreSQL и ключей по принятой процедуре. Не заменяйте рабочие настройки JWT, БД и APP_FIELD_ENCRYPTION_KEY. Добавьте в секреты:

```dotenv
TEXT_AGENT_ENABLED=true
AGENT_API_KEY=<ключ провайдера, только на сервере>
AGENT_MODEL_ENDPOINT=https://api.deepseek.com/chat/completions
AGENT_MODEL=deepseek-flash
AGENT_STATE_ENCRYPTION_KEY=<Base64 от 32 случайных байтов>
```

Отдельный ключ состояния создаётся один раз (`openssl rand -base64 32`) и сохраняется между deploy. Если он не задан, конфигурация использует существующий APP_FIELD_ENCRYPTION_KEY. Всем репликам нужен один стабильный ключ. Не меняйте его при обычном обновлении: старые сессии перестанут читаться. `.env` — права 600, не включать в Git. Ключ модели не нужен при сборке и не попадает во frontend.

```sh
git fetch origin
git switch --track origin/codex/text-agent-production
```

Для существующей локальной ветки: `git switch codex/text-agent-production` и `git pull --ff-only`. Сначала проверьте локальные изменения.

На текущем сервере Rental Management работает как Compose project **rentcrm**, с **обоими** файлами. Сохраняйте этот набор и существующие volumes:

```sh
docker compose -p rentcrm -f docker-compose.yml -f docker-compose.override.yml config --quiet
docker compose -p rentcrm -f docker-compose.yml -f docker-compose.override.yml up -d --build backend frontend
docker compose -p rentcrm -f docker-compose.yml -f docker-compose.override.yml ps
```

Не используйте `down -v`. V10 применяется автоматически до старта JDBC-хранилища. Миграция добавляет таблицы и не удаляет бизнес-данные. Сначала проверьте эту ветку на staging-копии: текущая доработка сама по себе не означает обновление рабочего сервера.

Откат: вернуть предыдущие образы backend/frontend и настройки, сохранив БД и ключи. Для текущей Flyway-настройки старое приложение с миграциями только до V9 допускает уже применённую будущую V10; проверить health после отката. Не удалять agent-таблицы вслепую: в них могут быть неоконченные попытки. При строгой политике миграций используйте подготовленный совместимый rollback-артефакт, а не удаление истории Flyway.

## Проверка

- Неавторизованный OpenAPI и agent endpoints недоступны.
- Неполный запрос запрашивает поля; неверный email/дата/сумма отклоняются до подтверждения.
- Создание арендатора до подтверждения не меняет БД, после создаёт ровно одну запись.
- Обновление страницы, повтор подтверждения и перезапуск backend возвращают сохранённый итог.
- Список арендаторов показывает данные только текущего аккаунта.
- Смена OpenAPI аннулирует старые неподтверждённые действия.
- UNKNOWN требует проверки результата в приложении и не запускает retry.

Для генерации и проверки контракта:

```sh
mvn -f backend/pom.xml -Dtest=OpenApiContractTest -Dagent.openapi.export=true test
mvn -f backend/vendor/text-agent/pom.xml clean install
mvn -f backend/pom.xml -Ptext-agent test
cd frontend
npm ci
VITE_TEXT_AGENT_ENABLED=true npm run build
```

При изменении моделей сначала обновите snapshot, затем синхронизируйте копию контракта в тестах/примерах библиотеки. Обычный OpenApiContractTest без export останавливает сборку при расхождении схемы с кодом. Политика доступных операций — OpenApiConfiguration.

## Ограничения и эксплуатация

Это кандидат для production-проверки. Транзакционной обработки Idempotency-Key в бизнес-API пока нет, поэтому exactly-once не обещается. Потеря ответа/5xx может означать завершённую операцию; повторять создание вслепую нельзя. CAS сохраняет правило одной отправки для одного confirmation ID, а новый текст создаёт новое предложение.

По умолчанию: 24 часа сессии, 3 минуты подтверждения, 20 команд/минуту и 60 status-запросов/минуту на пользователя, 20 сессий на пользователя, 10000 всего; audit 30 дней. Очистка каждую минуту. Планируется мониторинг стоимости/ошибок модели и нагрузочные испытания. APP JWT продолжает определять права, выделенных agent scopes пока нет.

Текст и черновик отправляются DeepSeek без маскирования, как согласовано. JWT и ответы бизнес-API модели не передаются. Шифрование состояния в БД не является маскированием данных для облачного провайдера.

Сквозная проверка воспроизводится командой `python3 scripts/test-text-agent.py` после сборки jar. Обязательны AGENT_TEST_PG_URL, AGENT_TEST_PG_USER и AGENT_TEST_PG_PASSWORD, указывающие только на отдельную временную БД. Тест применяет миграции, создаёт синтетические аккаунты и арендатора, перезапускает локальное приложение. На рабочую БД его запускать нельзя. CI создаёт собственную PostgreSQL для этого сценария.
